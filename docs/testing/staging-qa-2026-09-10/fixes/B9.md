# B9 — Payout maker-checker and the NEFT bank-upload file (fix results)

Branch `fix/staging-qa-2026-09-10`. Findings in the order worked: F94, then
F44 / F95 (and F28's consumer half).

## F94 — fixed

Commit `73a0e85b`.

`approve`, `reconcile` and `retry` all shared `can:finance.record`, so
`admin-finance` could build a payout batch, approve it, pull the bank file and
record the bank's response — the whole money path in one role, against a staff
login with no MFA. `payout_batches` recorded `approved_by` but no maker, so
"the maker approved their own batch" was not representable, let alone blocked.

- `app/database/seeders/RolesAndPermissionsSeeder.php` — new permission
  `finance.approve` in `SUPER_ONLY`: `admin` and `developer` only. Strictly
  additive (`firstOrCreate` + `givePermissionTo`), so it is safe to re-run on
  staging. Deliberately NOT `admin-finance` (which keeps making and settling)
  and not `admin-compliance` (which has no part in the payment run).
- `app/database/migrations/2026_09_11_110000_add_created_by_to_payout_batches.php` —
  nullable `created_by` with an FK to `users` (`nullOnDelete`), matching the
  existing `approved_by` column. Guarded by `hasColumn`, so it is a no-op where
  drift already added it.
- `PayoutService` — `batchCreatorId()` reads the maker from the two places one
  can exist: `Auth::id()` for an admin acting on a payout page, and
  `EngineRunContext::actorId()` for a run started from the Engine Runs console,
  where the command executes on a queue worker with no session. The scheduler
  has neither and its batches are stamped NULL. Both `PayoutBatch::create()`
  calls (weekly + monthly) stamp it; a re-run of a batch that has no maker picks
  up whoever re-ran it, and an existing maker is never overwritten — the first
  hand on the batch is the one barred from approving it.
- `HandlesPayoutBatchActions::approve()` — refuses when
  `created_by === auth()->id()`, with a flash back to the batch page and a
  `payout.batch.self_approval_refused` audit row (actor, batch, maker, net).
- `routes/web.php` — both approve routes moved to `can:finance.approve`;
  `neft`, `reconcile`, `retry-failed` and `line-items.retry` stay on
  `finance.record` as specified.
- Both batch views — the Approve button is hidden without `finance.approve` or
  when the viewer is the maker, with an amber note explaining why; the line
  under the action bar now reads "Created by … / Approved by … on …" and says
  "the scheduler" for an unattributed batch.
- `app/resources/help/payout-operations.md` — new "Who may approve a batch"
  section (both rules, plus the scheduler case) and the new audit action in the
  audit-trail table.
- `docs/compliance/risk-register.md` — new **R-81**, closed 2026-09-11, with the
  accepted residual (a scheduler-built batch is approvable by any single
  approver, because its maker is a cron job).

Tests (`PayoutAdminPagesTest`): "keeps approving a payout batch out of the hands
that build and settle it" (admin-finance holds `finance.record` but not
`finance.approve` → 403, batch still pending; admin approves); "refuses to let
the admin who created a batch approve it" (refusal + audit row + the page copy +
a second approver succeeding); "lets any approver sign off a batch the scheduler
built"; "stamps the admin who ran the batch as its maker" (via
`EngineRunContext`). 14 passed on SQLite and on MySQL (`arovolife_test`,
container) — the FK migration applies on both.

`SeparationOfDutiesTest` / `AdminRoleSeparationTest` / `PayoutServiceTest` /
`tests/Feature/Compensation` all still green (131 passed).

**Deploy note:** `RolesAndPermissionsSeeder` must be re-run on staging and
production after this deploy, or nobody holds `finance.approve` and no batch can
be approved. (Decision Q17 already flags the same re-run for `content.publish`.)

## F44 / F95 — fixed (and F28's consumer half)

Commit `afa453e7`.

The export emitted `Line#, ADN, Full Name, Bank Last 4, Net Amount (₹), UTR,
Status` — no account number, no IFSC — while the approval flash told finance to
"upload it to the bank". Per client decision Q5 it is now a real bank-upload
file.

- `PayoutService::bankInstructionForDistributor()` — new, next to
  `bankLast4ForDistributor()` so the PiiCrypter pattern stays in one place.
  Returns the account number (decrypted; a failure throws
  `BankDecryptionException` exactly as the batch run does, and logs `critical`
  without the ciphertext), the IFSC (stored plain — a public branch code) and
  the beneficiary name. The name comes from B10's
  `distributors.bank_beneficiary_name_enc` (landed in `1fc7eecc`), decrypted via
  a private `beneficiaryName()` that **never** throws: an absent or unopenable
  name falls back to `users.full_name`, because a name mismatch is a bank
  rejection while a missing account number is a wrong payment.
- `HandlesPayoutBatchActions::exportNeft()` — columns are now
  `Line#, ADN, Beneficiary Name, Account Number, IFSC, Net Amount (₹),
  Narration, UTR, Status`. Amount stays ungrouped with two decimals; every cell
  still goes through `Csv::safe()`. Narration is `arovolife <ADN> B<batch id>` —
  short enough to survive NEFT remittance-info truncation, and it names the
  payer, the payee's ADN and the batch. Filename is now
  `bank-upload-<type>-<date>.csv`.
- The file is built into `php://temp` and materialised before anything is sent,
  because the audit row has to carry a digest of the bytes the admin actually
  received. Each download writes `payout.batch.bank_file_exported` with actor,
  batch type/date, line count, batch net and
  `after_hash = AuditLog::digest($csv)` (raw 32 bytes, never hex). No account
  number, name or file body reaches the audit row, a flash or any log.
- A line whose ciphertext no longer opens (a key rotation between the batch run
  and the download) is exported with `Account Number` and `IFSC` blank and
  `Status` reading `bank_decrypt_failed`: it cannot be executed by mistake and
  it is not silently missing from the file.
- Copy: the button is **Download bank file (NEFT)** on both batch pages; the
  approval flash, both approve-confirm modals and the Payout Settings page no
  longer say "NEFT CSV". The reconciliation-sheet wording that claimed the file
  goes to the bank is now true.
- `app/resources/help/payout-operations.md` — new "The bank file (NEFT)"
  section (column table, the per-download audit row, the decrypt-failure line),
  plus the renamed button through the mode table and the manual-NEFT steps, and
  the new audit action in the audit-trail table.
- `docs/compliance/risk-register.md` — new **R-82** (Mitigated): the export is
  now a DPDP disclosure surface; controls and the accepted residual (a finance
  user can retain a legitimately downloaded file; the digest makes it
  attributable) are recorded there.

The gate half of F95 (approved batches only, `can:finance.record`, button
hidden) was already done in B3 and is untouched.

Tests (`PayoutAdminPagesTest`): "exports a bank file the bank can execute, and
audits every download" — asserts the decrypted account numbers and IFSCs for two
fixture distributors, the given beneficiary name and the `full_name` fallback,
the ungrouped amount, the narration, the audit row's actor/line count, that
`after_hash` equals the digest of the streamed bytes, and that no account number
appears in the audit details; "exports a line whose bank details no longer
decrypt with no account number". 16 passed on SQLite; 18 passed on MySQL
(`arovolife_test`, container) together with `PayoutBankDecryptionTest` — which
matters here, because `after_hash` is `BINARY(32)` and
`bank_beneficiary_name_enc` is `VARBINARY(512)`, neither of which SQLite models.

`PayoutServiceTest` + `tests/Feature/Compensation`: 133 passed. `pint --dirty`
clean; `phpstan` clean on both changed PHP files.

### Notes for the orchestrator

- **Deploy step, blocking:** `RolesAndPermissionsSeeder` must be re-run on
  staging and production after this deploy. Until it is, nobody holds
  `finance.approve` and **no payout batch can be approved**. (Decision Q17
  already schedules the same re-run for `content.publish`.)
- **Operational change to flag to finance:** approving a batch is no longer
  `admin-finance`'s to do. If the only staff account in daily use is an
  admin-finance login, someone with the `admin` role has to be available on
  payout day, or the weekly run sits unapproved.
- **Narration format is a decision the client may want to see:**
  `arovolife <ADN> B<batch id>` is what will appear on distributors' bank
  statements. Changing it later changes what every future statement says; if the
  client wants the batch *date* rather than the batch id, say so before the
  first live run.
- The old column `Bank Last 4` is gone from the export. The bank-response import
  matches on **ADN** and (F14) an amount column, neither of which changed, so
  reconciliation is unaffected.
