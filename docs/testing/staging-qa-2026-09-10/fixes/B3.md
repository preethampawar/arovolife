## F52 / F89 — fixed

Non-income rows counted as income on the distributor dashboard and on the admin
"Pending payouts" tile.

- `app/app/Modules/Compensation/Services/WalletService.php` — `creditTotalsByMonth()`
  now excludes `self::REPURCHASE_TYPES`, exactly as `balancePaise()` does.
  `repurchase_deduction` is a POSITIVE row (the credit landing in the repurchase
  wallet), so it was counted as income by the THIS MONTH tile, the totals row and
  the six-month chart — which is why THIS MONTH could exceed LIFETIME by the size
  of the deduction.
- `app/app/Modules/Compensation/Http/Controllers/Admin/CompensationOverviewController.php` —
  `$pendingPayoutPaise` now sums main-wallet types only (same exclusion), so the
  tile reports cash payable rather than the whole ledger.
- `app/resources/views/admin/compensation/overview.blade.php` — tooltip now says the
  figure is cash payable only.

Tests: `WalletServiceTest` → "creditTotalsByMonth ignores the repurchase-wallet credit
so a month can never exceed lifetime income"; `PayoutAdminPagesTest` → "excludes the
repurchase wallet from the admin Pending payouts tile".

## F14 — fixed

NEFT import validated no amounts.

- `app/app/Modules/Compensation/Services/PayoutReconciliationService.php` — recognises
  an amount column (`Net Amount`, `Amount`, `Transfer Amount`, …) and refuses any row
  whose amount differs from that line's `net_transferred_paise`. Rejected rows land in
  a new `rejected` summary list with the two figures, are counted in the flash message
  and in the `payout.batch.reconciled` audit row, and change nothing. A blank amount
  cell is not a mismatch (banks leave it empty on a return). When the file carries no
  amount column at all, `amount_checked` is false and the admin is told amounts went
  unverified.
- `app/app/Modules/Compensation/Http/Controllers/Admin/AdminWeeklyPayoutController.php` —
  reports rejected counts and the unverified-amount note.
- `app/resources/help/payout-operations.md` — documents both refusals.

Tests: `PayoutGatewayGuardsTest` → "rejects a bank row whose amount does not match the
line it names"; "settles a row whose amount matches and reports that amounts went
unchecked when the column is absent".

## F15 — fixed

No duplicate-UTR guard and no unique constraint.

- `PayoutReconciliationService` — a UTR already recorded on any payout line (this file
  or an earlier import, any batch) is rejected rather than applied.
- `app/database/migrations/2026_09_11_100000_add_unique_index_to_payout_line_items_utr.php` —
  nullable unique index `uniq_payout_line_items_utr`. Idempotent
  (`whenTableDoesntHaveIndex`). Refuses to run, naming the offenders, if the table
  already holds a duplicate reference: that is a double payment for a human to
  reconcile, not something a schema change should paper over. Dev MySQL checked —
  0 UTRs recorded, 0 duplicate groups.

Tests: `PayoutGatewayGuardsTest` → "refuses to settle two lines against one bank
reference"; "refuses a reference already recorded by an earlier batch"; "the database
refuses two line items sharing one UTR". Verified on SQLite and on MySQL
(`arovolife_test`, container): 25 passed both.
