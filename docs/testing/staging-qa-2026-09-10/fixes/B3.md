## F52 / F89 — fixed

Non-income rows counted as income on the distributor dashboard and on the admin
"Pending payouts" tile.

- `app/app/Modules/Compensation/Services/WalletService.php` — `creditTotalsByMonth()`
  now excludes `self::REPURCHASE_TYPES`, exactly as `balancePaise()` does.
  `repurchase_deduction` is a POSITIVE row (the credit landing in the repurchase
  wallet), so it was counted as income by the THIS MONTH tile, the totals row and
  the six-month chart — which is why THIS MONTH could exceed LIFETIME by the size
  of the deduction.
- `app/app/Modules/Compensation/Http/Controllers/Admin/CompensationOverviewController.php` —
  `$pendingPayoutPaise` now sums main-wallet types only (same exclusion), so the
  tile reports cash payable rather than the whole ledger.
- `app/resources/views/admin/compensation/overview.blade.php` — tooltip now says the
  figure is cash payable only.

Tests: `WalletServiceTest` → "creditTotalsByMonth ignores the repurchase-wallet credit
so a month can never exceed lifetime income"; `PayoutAdminPagesTest` → "excludes the
repurchase wallet from the admin Pending payouts tile".

## F14 — fixed

NEFT import validated no amounts.

- `app/app/Modules/Compensation/Services/PayoutReconciliationService.php` — recognises
  an amount column (`Net Amount`, `Amount`, `Transfer Amount`, …) and refuses any row
  whose amount differs from that line's `net_transferred_paise`. Rejected rows land in
  a new `rejected` summary list with the two figures, are counted in the flash message
  and in the `payout.batch.reconciled` audit row, and change nothing. A blank amount
  cell is not a mismatch (banks leave it empty on a return). When the file carries no
  amount column at all, `amount_checked` is false and the admin is told amounts went
  unverified.
- `app/app/Modules/Compensation/Http/Controllers/Admin/AdminWeeklyPayoutController.php` —
  reports rejected counts and the unverified-amount note.
- `app/resources/help/payout-operations.md` — documents both refusals.

Tests: `PayoutGatewayGuardsTest` → "rejects a bank row whose amount does not match the
line it names"; "settles a row whose amount matches and reports that amounts went
unchecked when the column is absent".

## F15 — fixed

No duplicate-UTR guard and no unique constraint.

- `PayoutReconciliationService` — a UTR already recorded on any payout line (this file
  or an earlier import, any batch) is rejected rather than applied.
- `app/database/migrations/2026_09_11_100000_add_unique_index_to_payout_line_items_utr.php` —
  nullable unique index `uniq_payout_line_items_utr`. Idempotent
  (`whenTableDoesntHaveIndex`). Refuses to run, naming the offenders, if the table
  already holds a duplicate reference: that is a double payment for a human to
  reconcile, not something a schema change should paper over. Dev MySQL checked —
  0 UTRs recorded, 0 duplicate groups.

Tests: `PayoutGatewayGuardsTest` → "refuses to settle two lines against one bank
reference"; "refuses a reference already recorded by an earlier batch"; "the database
refuses two line items sharing one UTR". Verified on SQLite and on MySQL
(`arovolife_test`, container): 25 passed both.

## F93 — fixed

Hold reasons were frozen at batch creation and never re-read.

- `PayoutService` — the four income gates now live in one ladder,
  `holdStatusFor()`, asked both when a line is built and again later. The
  per-distributor bodies of `runWeeklyBatch()` / `runMonthlyBatch()` were
  extracted to `processWeeklyDistributor()` / `processMonthlyDistributor()` so a
  cleared hold can be replaced by a real payable line using exactly the code that
  builds every other line — no second implementation of the deductions or sweep.
- New `releaseClearedHolds()`, called at approval **and** at a re-run of an
  existing batch (the per-distributor guard skipped anyone who already had a
  line, so a hold could never clear inside its own batch). A hold that has
  cleared is deleted and re-processed into the same batch; a hold that still
  stands for a *different* reason is restated. Either way one
  `payout.batch.holds_reevaluated` audit row records what changed, and
  `payout.batch.approved` carries `holds_released_at_approval` /
  `holds_restated_at_approval`.
- Batch totals are re-derived before the approval is signed off, so the amount an
  admin confirms is the amount that goes out.
- `app/resources/help/payout-operations.md` — documents the re-read at approval.

Tests (`PayoutServiceTest`): "releases a hold that cleared before approval, into
the batch being approved" (bank + KYC added after creation → payable after
approve, batch count/net updated, audit row written); "restates a hold whose
reason changed instead of approving a stale one"; "releases a hold that cleared
before a re-run of the same batch".

## F48 — fixed

The monthly batch had no earning window and `earnings_through` was never stamped.

- `WalletLedgerEntry::earnedForMonthOrBefore()` — a new scope, the monthly
  counterpart of `earnedOnOrBefore()`. Three readings of "when was this earned",
  in order of authority: `bonus_month <= month` (what the monthly engines stamp
  when they close a month on the 1st of the next), else `earned_on <= month end`,
  else `created_at <= month end` for a credit with neither (a Lifetime Award
  released by hand). Legacy rows with neither column fall to `created_at`, which
  for a historical batch is the answer the old unwindowed sweep gave.
- `PayoutService::runMonthlyBatch()` stamps `earnings_through` = last day of the
  month it pays, and the window is applied to the distributor selection, the
  per-distributor entries query, the credit-time `repurchase_transfer` sweep and
  the held-line totals — so a held monthly line reports only the month its batch
  covers.
- `WalletService::sumUnsweptByTypes()` and `PayoutService::unsweptRepurchaseTransfers()`
  / `holdLineItem()` take the month window alongside the existing weekly one.
- ADC was the one monthly stream credited with `bonus_month` NULL, so the new
  window would have pushed every ADC credit a month late. It is now stamped with
  the month the centre served (committed separately as F09, `cd1ddaa0`).
- `app/resources/help/payout-operations.md` — the monthly batch pays one month.

Tests (`PayoutServiceTest`): "leaves next month's income unswept when it pays a
month" (August's batch pays the August credit and leaves the September one in the
wallet; September's batch pays it); "stamps the last day of the month it pays
onto the monthly batch it creates"; "leaves an ADC credit with no earned month to
the batch for the month it was written in". Eight existing monthly tests were
updated to stamp `bonus_month` on their credits, which is what the engines do.

## F45 — fixed

The weekly sweep, the monthly sweep and (now) approval all read the remaining room
under the shared ₹50L monthly ceiling and then spend it; only the clock separated
them.

- `PayoutService::withSweepLock()` — one cache lock (`compensation:payout-sweep`,
  1h TTL, 120s wait) wraps `runWeeklyBatch()`, `runMonthlyBatch()` and
  `approve()`. Blocking rather than refusing: a batch that will not start is a
  batch that does not pay, so the second caller waits and then sweeps what is
  left. A `LockTimeoutException` is what the run commands already turn into a
  failed batch and a non-zero exit.

Test (`PayoutServiceTest`): "holds one sweep lock for the whole batch, so two
sweeps cannot share a ceiling" — a second acquire from inside the sweep fails,
for both batch types.

## F97 — fixed

- New trait `Compensation/Http/Controllers/Admin/Concerns/HandlesPayoutBatchActions`
  holds approve / reconcile / retry / retry-one / exportNeft; both payout
  controllers use it and supply their own `payoutRouteName()`. New
  `monthly-payouts/*` routes for all five actions, same `can:finance.record`
  guards, and the monthly view now posts to them and is redirected back to
  itself. Every monthly button used to post at `weekly-payouts/*` and bounce the
  admin onto the weekly page.
- "Wallet balance" column renamed **Payable before deductions**, with a tooltip

  credit time). The old tooltip claimed it was the wallet balance at batch
  generation, which it is not.
- `heldTotals()` feeds both confirm modals: they now name the held income and how
  many distributors it belongs to alongside the net being approved, so a batch of
  nothing but holds no longer reads as "₹0.00 to 0 distributor(s)".
- Approval impact copy says holds are re-checked first (F93).

Test (`PayoutAdminPagesTest`): "posts the monthly batch actions at the monthly
routes and names the held income before approval".
