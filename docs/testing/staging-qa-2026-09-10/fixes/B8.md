## F24 — `repurchase:evaluate` writes a run summary — **fixed**

Files:
- `app/app/Modules/Compensation/Console/Commands/RepurchaseEvaluateCommand.php`
- `app/tests/Modules/Compensation/RepurchaseEvaluateCommandTest.php` (new)

The run now attaches its counts to its own `engine_runs` row:
`outcome`, `as_of`, `evaluated`, `fulfilled`, `forfeited`, `withheld`, `no_cycle`, `failed`,
`failed_adns`, `failure_classes`, `reason`. The Engine Runs events page already renders any
extra summary key as a labelled field, so this needs no view change.

Two decisions worth recording:

1. **Where the summary is written.** `RecordEngineRun` (out of scope for this batch, and
   correctly so) only writes `summary` for a declared outcome or a flag-off no-op; on the
   plain success/failure path it leaves the column alone. So the command writes the summary
   itself, onto the run id it gets from `EngineRunContext::activeRunId()`, and the listener's
   close-out preserves it. The cost of not touching the listener: on a `failed_partial` run
   the row's `error` column carries the listener's generic "exited with code N without
   recording a reason" line rather than the engine's own sentence — because declaring an
   outcome via `noteFailed()` would have *replaced* the structured summary with
   `{"reason": …}`. The reason sentence is in the summary instead, which is what the page
   shows. Follow-up for whoever owns `RecordEngineRun` next: let an engine declare a status
   without surrendering its summary, and this asymmetry goes away.
2. **`fulfilled` / `forfeited` are verdicts, not a census.** A fulfilled window rolls into
   the next one inside the same `evaluate()` call, so the returned cycle is almost always
   the fresh active one — counting returned statuses would have reported `fulfilled: 0`
   forever. They are counted instead from `repurchase_cycles.resolved_at >= run start`,
   which is stamped exactly once per window. `withheld` is the separate standing count of
   distributors whose current cycle is suspended — the number that answers "who is not
   earning tonight".

Console line is now
`Done — evaluated: N, fulfilled: N, forfeited: N, withheld: N, failed: N`.

Tests: `RepurchaseEvaluateCommandTest` — "writes the run counts to the engine run summary",
"counts the verdict it takes when a window closes fulfilled", "counts a lapsed window as
forfeited and the distributor as withheld".

## F23 — one throwing distributor must not stall the platform — **fixed**

Files:
- `app/app/Modules/Compensation/Console/Commands/RepurchaseEvaluateCommand.php`
- `app/app/Modules/Compensation/Console/Commands/GsbDailyCutoffCommand.php` (refusal branch only)
- `app/app/Modules/Compensation/Services/EngineStatusService.php` (one new read method)
- `app/resources/help/compensation.md`
- `app/tests/Modules/Compensation/{RepurchaseEvaluateCommandTest,GsbDailyCutoffCommandGuardTest}.php`

Per-distributor isolation was **already** in place (the loop caught `Throwable` and carried
on); what was missing was any record of *who* failed. The run now collects the failed
distributor ids, resolves them to ADNs (capped at 50; the log has them all), records the
exception **classes only** — never the messages, which can carry whatever the data put in
them — and writes them into the `failed_partial` summary. Exit code is unchanged: non-zero
when the failure count is non-zero.

**The documented choice.** The cut-off gate still refuses platform-wide on any non-zero
failure count, and that is deliberate:

- A `failed_partial` run is recorded `failed`, so `hasSucceededRunAfterDay()` — the existing
  gate — is unmoved. Failure count zero ⟹ the run is `succeeded` ⟹ the gate opens. The two
  formulations coincide; the gate is already "refuses only when the failure count is
  non-zero".
- Refusing *only for the named distributors* was considered and rejected: the cut-off freezes
  the day's GSB and MSB pools once, for everybody, and never reprices them. Running the day
  without the failed distributors' BV would price every other distributor's match against a
  pool that is permanently short — a much larger, silent error than a stalled night that an
  operator can see and fix.
- What changes is the diagnosis. The refusal message and the
  `gsb.cutoff.refused_missing_evaluate` log entry now name the failing ADNs and exception
  classes, read from the run's summary via the new
  `EngineStatusService::latestRunAfterDay()` (same "saw the whole day" predicate as the gate,
  status-agnostic; the predicate is now one shared private closure used by both methods).
  D4's blast radius stands; the time to clear it drops from "read the log on the server" to
  "read the refusal".

Tests: "carries on past a throwing distributor and evaluates the rest" (distributors before
*and* after the throwing one are still evaluated), "records a failed_partial summary naming
the failed ADNs and the exception class", and in the guard test "names the distributors the
evaluation could not judge when it refuses" + "says nothing about failures when the
evaluation simply never ran".

Help doc updated in the same change (`resources/help/compensation.md`, the cut-off refusal
section).

## F22 — open windows keep the `start+29` due date — **fixed**

Files:
- `app/app/Modules/Compensation/Database/Migrations/2026_09_11_100000_redate_open_repurchase_cycles_to_full_window.php` (new)
- `app/tests/Modules/Compensation/RedateOpenRepurchaseCyclesMigrationTest.php` (new)

Forward-only, idempotent: any cycle with `resolved_at IS NULL` whose `due_date` is exactly
`cycle_start_date + 29` is re-dated to `+ 30`. Row-by-row in PHP rather than a SQL date
expression, because MySQL and SQLite spell date arithmetic differently and the affected set
is tiny (7 rows on staging). After one run no row matches the predicate, so re-running is a
no-op.

Scope decisions:
- `resolved_at IS NULL` is the test for "open", not `due_date >= today`. An unresolved window
  has not been judged yet whichever side of today its due date falls on, and it should be
  judged on the current rule.
- A **resolved** cycle is never touched: its verdict is frozen against its own due date, and
  moving that date would make the freeze describe a window that no longer exists.
- Only the documented off-by-one is corrected. A window short for any other reason (a
  non-default `comp.repurchase.cycle_days`, say) is left alone — that needs a decision, not a
  silent nudge. The 30 is a constant in the migration, with a comment saying so.

Tests: full-30 re-date, already-correct row untouched, idempotence, resolved row untouched,
other-length window untouched.

## F21 — the backfill migration's missing `due_date < today` guard — **fixed**

Files:
- `app/app/Modules/Compensation/Database/Migrations/2026_09_06_100003_backfill_verdicts_on_existing_repurchase_cycles.php`
- `app/tests/Modules/Compensation/BackfillRepurchaseCycleVerdictsMigrationTest.php`

`whereDate('due_date', '<', today)` added to **both** updates — the `completed` one and the
`grace|suspended` one — which is what the docblock already claimed ("Cycles still inside
their window are untouched"). Strictly less-than: a window due today closes at 23:59 and is
still in flight.

Editing an already-deployed migration rather than writing a compensating one is the
instruction for this finding and is safe here: production has not run it (the repurchase flag
is off there, R-75), and the seven staging rows it damaged are cleaned by F10's windowed
recompute. Nothing in the fix depends on the damaged rows.

Note carried forward, **not** fixed here (out of the fix-plan's scope for F21): a premature
*completed* verdict still has no undo path — `RepurchaseCycleService::refresh()` resets a
premature **failed** verdict only (`elseif ($cycle->status !== STATUS_COMPLETED)`). With the
guard in place nothing new can create one, and the existing seven are cleaned by F10, so
there is no live exposure; but if a completed-verdict row is ever frozen prematurely again,
nothing self-heals it. Worth a follow-up ticket rather than an unrequested change to the
engine's undo logic.

Tests added: "leaves a COMPLETED cycle whose window is still open untouched", "leaves a
window closing TODAY untouched, because it closes at 23:59", "leaves a suspended cycle whose
window is still open untouched". The four pre-existing tests are unchanged and still pass
(they all use windows that closed months ago).
