## F59/F54 (follow-up) — fixed

Commit `d53c3954`.

Order status changes write a `database` notification (B6, `1c5aa8d6`), but
the bell (B5b, `_notification-bell.blade.php`, F54) only counted unread
messages and announcements, so a shipment/delivery notice never surfaced
there. No distributor-facing notifications list existed at all.

- `app/app/Modules/Identity/Http/Controllers/NotificationController.php`
  (new) — `index()` lists the signed-in user's own `notifications()` (paginated,
  newest first); `open($id)` marks one read and redirects to its `data['url']`
  when the notification carries one, else back to the list. Ownership is
  enforced by resolving through `$user->notifications()` (a stranger's id
  404s).
- `app/resources/views/notifications/index.blade.php` (new) — title/body/time
  list, styled like `announcements/index.blade.php`; unread rows get a "New"
  badge.
- `app/routes/web.php` — `GET /notifications` (`notifications.index`) and
  `GET /notifications/{id}/open` (`notifications.open`), inside the existing
  `auth + kyc.rejected.resubmit` group. Not flag-gated — the database channel
  is always on, unlike messaging/announcements.
- `app/resources/views/partials/_notification-bell.blade.php` — adds a third
  unread count (`auth()->user()->unreadNotifications()->count()`), a third
  `$bellDestination` branch ('notifications', chosen only when messages and
  announcements are both zero), and keeps the bell visible whenever there is
  an unread notification even if both feature flags are off (previously the
  bell disappeared entirely with both flags off).
- `app/tests/Modules/Identity/NotificationControllerTest.php` (new) — NC-01
  (index shows title/body/time), NC-02 (opening marks read + redirects to the
  order URL), NC-03 (another user's notification 404s), NC-04 (bell counts it
  and routes to `notifications.index` when it's the only unread thing).
- `app/phpstan-baseline.neon` — one new entry (`actingAs()`, count 4, for the
  new test file).

Test: `php artisan test --filter="NotificationControllerTest|AnnouncementTest|MessageFlowTest"` — 24 passed (announcements/messaging bell paths unaffected).

## F34 (follow-up) — fixed

Commit `fe79d817`.

`ProductCatalogSeeder` pointed three `image_url`s (`AV-IB-001`, `AV-VCS-001`,
`AV-AFW-001`) at `picsum.photos` — a random-image placeholder service. No
local placeholder asset exists elsewhere in the codebase to point at instead,
and the storefront already has a proper null-safe fallback
(`Product::primaryImageUrl()`, B6/F34's original fix, `efd5a038`) that shows a
generic icon when a product has no picture — so these three are now `null`.

- `app/database/seeders/ProductCatalogSeeder.php` — the three `image_url`
  values set to `null`; top-of-method comment updated to explain why.
- `app/tests/Modules/Admin/ProductCatalogSeederTest.php` — PCS-01 now asserts
  `image_url` is `null` for those three SKUs (was `toStartWith('https://')`)
  and adds an explicit guard that no seeded product's `image_url` contains
  `picsum.photos`.
- `app/phpstan-baseline.neon` — the two now-invalid entries removed (both
  embedded the old picsum literals inside the full array-shape signature for
  the `nullCoalesce.offset` check on `database/seeders/ProductCatalogSeeder.php`);
  replaced with the one entry that still legitimately fires (the `'dist'` key
  offset — `image_url`'s own offset warning disappeared on its own, since the
  value type now legitimately includes `null`, so the `??` there is no longer
  dead code).

Test: `php artisan test --filter=ProductCatalogSeederTest` — 3 passed (SQLite,
`RefreshDatabase`, `DatabaseSeeder` order mirrored via `ProductCategorySeeder`
then `ProductCatalogSeeder`).

## Note: pre-existing phpstan single-file isolation drift

Several files (`AdminCatalogTest.php`, `DistributorRequestTest.php`) show a
baseline `ignore.count` mismatch (e.g. "expected 21 times, but occurred only
20 times") for patterns unrelated to anything in this batch, when `phpstan
analyse` is run against that one file in isolation rather than the full
suite. Verified on each file by stashing this batch's changes and re-running
— the mismatch is identical with or without this batch's diff, so it
predates B14 and was left alone (out of scope; not introduced here).
