## F05 — fixed

`EngineStatusService::hasSucceededRun()` matched engine + period date + status, so a run stamped
INSIDE its own period counted as a completed period. It now also requires `started_at` at or after
the first instant following the period — the next day for a date engine, the first of the next month
for a month engine (`EngineStatusService::periodEndsAt()`), the same rule `hasSucceededRunAfterDay()`
already applied to the daily cut-off.

The payout-close half is in `MonthlyEngineCompletionGate::blockingFailure()`: a succeeded run that
started while the month was in flight no longer satisfies the gate; it refuses with the new reason
`succeeded_in_flight`, naming the run and when it ran.

- Files: `app/app/Modules/Compensation/Services/EngineStatusService.php`,
  `app/app/Modules/Compensation/Support/MonthlyEngineCompletionGate.php`
- Tests: `EngineStatusServiceTest` — "hasSucceededRun rejects a month-typed run that started while
  the month was still in flight", "…accepts a month-typed run that started once the month had
  closed", "…rejects a date-typed run that started before the day ended";
  `MonthlyCloseCommandTest` — "does not resume past a step whose succeeded run started while the
  month was still in flight"; `MonthlyPayoutCloseCommandTest` — "refuses when every run for an
  engine started while the month was still in flight".
- Commit: 35d6b7ad (see note above).
- Follow-up: `isPeriodComputed()` inherits the stricter rule, so the chain resolver may now re-run a
  prerequisite whose only run happened inside its period (repurchase evaluation, most often). That is
  the same reasoning as the cut-off's own guard and is cheap; noted rather than special-cased.

## F40 — fixed

The gate read only the seven crediting engines, so a close that aborted before step 1 (stale worker,
a daily cut-off that never finished) left every engine carrying an OLDER succeeded run and the month
read "ready to pay". `blockingFailure()` now also reads `compensation.monthly-close`'s own runs for
the month and refuses on an unresolved failure (reason `close_failed`), naming the re-run command.

- Files: `app/app/Modules/Compensation/Support/MonthlyEngineCompletionGate.php`
- Tests: `MonthlyPayoutCloseCommandTest` — "refuses when the monthly close itself failed and has not
  succeeded since", "pays once the failed close has been re-run successfully".
- Commit: 35d6b7ad.

## F47 — fixed

`payout:monthly-run` now: resolves `--month` through `ResolvesMonthOption` (default = the month that
has just ended, was the month in flight); refuses a batch month that has not closed unless
`--in-flight`; and runs `MonthlyEngineCompletionGate` against the CREDITING month (batch month − 1),
refusable only with `--force`. `payout:monthly-run` was added to `OpenMonthGuard::FREEZING_COMMANDS`.

`--month` keeps its meaning — the batch month, the month the money moves. Changing it to the
crediting month (one reading of the fix spec's "default to the PREVIOUS month") would have contradicted
`EngineHealthService`, `EngineStatusService::lastComputedPeriod()` and every `payout.monthly` run row,
all of which date this engine by the batch month. The spec's four requirements are all met under the
batch-month reading; the batch's own sweep logic in `PayoutService` is untouched.

`compensation:monthly-payout-close` passes `OpenMonthGuard::overrideFor('payout:monthly-run', …)`,
because on the 8th the batch month IS the live month — that is the one sanctioned lift, and it is why
a hand-typed run still refuses.

- Files: `app/app/Modules/Compensation/Console/Commands/MonthlyPayoutCommand.php`,
  `…/MonthlyPayoutCloseCommand.php`, `app/app/Modules/Compensation/Support/OpenMonthGuard.php`,
  `app/app/Modules/Compensation/Services/Recompute/EngineReplayService.php`
- Tests: `PayoutCommandFailureTest` — "refuses a batch month that has not closed", "refuses while the
  month it pays has incomplete crediting", "defaults to the month that has just ended, never the live
  one"; `MonthlyPayoutCloseCommandTest` — "lifts the batch command's open-month refusal, because the
  batch month is in flight by design".
- Commit: 35d6b7ad.

## F31 — fixed

`gsb:daily-cutoff` refuses a `--date` that is today or later unless `--in-flight`, independently of
the repurchase gate, and `--force` does NOT lift it (that flag answers whether the day has been
judged). The refusal is logged (`gsb.cutoff.refused_open_day`) and recorded on the run as skipped with
its reason. `gsb:daily-cutoff` joined `OpenMonthGuard::FREEZING_COMMANDS` so the admin console's
developer gate and the replay hand it the same override they hand the monthly engines.

The recompute replay simulates the scheduler at each day's own instant, so every replayed day is
"today": the day loop now travels the clock before asking `OpenMonthGuard::overrideFor()` and passes
the result to the invocation (it also lifts the monthly batch's completion gate — a replay has just
rebuilt those engines itself, and refusing would abort the rebuild after the wipe).

- Files: `app/app/Modules/Compensation/Console/Commands/GsbDailyCutoffCommand.php`,
  `app/app/Modules/Compensation/Support/OpenMonthGuard.php`,
  `app/app/Modules/Compensation/Services/Recompute/EngineReplayService.php`
- Tests: `GsbDailyCutoffCommandGuardTest` — "refuses a cut-off for today…", "refuses a cut-off dated
  in the future", "--force does not lift the closed-day guard…", "--in-flight runs today
  deliberately…", "runs a closed day with no override at all". Existing same-day fixtures in
  `GsbDailyCutoffCommandTest` / `GsbIdleCutoffBatchTest` now pass `--in-flight` (they deliberately cut

## F07 — fixed

`purchase_offer_grants` added to `DerivedTables` (truncation list + `month_start`/month date
filter). The grant is also the idempotency guard (`PurchaseOfferService::alreadyGranted()`), so a
surviving grant made every later recompute skip the month — a distributor who crossed the qualifying
BV after a premature run was denied their offer permanently.

Wiping grants alone would have introduced a new defect: `grantRedeemPoints()` writes a
`redeem_point_entries` accrual per grant, so a re-grant would award the same points twice. The
accruals are therefore deleted **with their parent grant** (`deleteByParent`, narrowed to
`reference_type = purchase_offer_grant`) rather than by date — the accrual is written in the month
after the one it was earned for, so a date filter would strand a surviving grant's points and take a
deleted grant's. Redemptions and their refunds are purchases and stay. A full
`platform:reset-purchases` takes the whole ledger (added to `COMMERCE_TABLES`), because every row in
it hangs off a grant or an order and both are wiped.

- Files: `app/app/Modules/Compensation/Support/DerivedTables.php`,
  `…/Services/Recompute/CompensationStateWiper.php`, `…/Services/Recompute/WindowedStateWiper.php`,
  `app/app/Console/Actions/PurchaseDataResetAction.php`
- Tests: `DerivedTablesTest` — "registers the purchase-offer grants and the points they awarded";
  `WindowedRecomputeTest` — "takes a purchase-offer grant with the points it awarded, and leaves the
  ones outside the window".
- Commit: 04721883.
- Follow-up: a CONSUMED grant deleted by a windowed recompute is re-granted as `granted` while the
  order that consumed it survives (orders are not derived), so the discount could be taken twice.
  Out of this finding's remit — it needs a product decision on whether consumption is replayable.

## F08 — no code change needed; documented

Already covered by the self-heal. `FortuneBonusService::enrollEligible()` calls
`replacePrematureFreeze()` BEFORE it considers refusing, so a pool written by a stray mid-month run
that funded nothing is discarded and the month reopens — `FortuneBonusServiceTest` already proves it
("discards a pool frozen mid-month that funded nothing, refreezes at the full month BV and reopens

What actually kept September shut on staging was F05: the monthly close skipped `fortune.enroll`, so

since F30 (another batch) it writes a `compensation.premature_freeze_kept` audit row and is reported
by the health digest instead of being only a log line. Recorded on `enrollEligible()`'s docblock.

### Things the next reader should know

1. **Commit boundary.** F05/F40/F47/F31 are inside **35d6b7ad**, a B1 commit, because another
   implementer ran `git commit` while those files were staged in the shared tree. Nothing is lost;
   the message just does not mention them. Everything after that is committed by path.
2. **`payout:monthly-run --month` still means the BATCH month** (the month money moves), not the
   crediting month. The fix spec's "default to the PREVIOUS month" is implemented as: the default is
   now last month, an open batch month is refused, and the gate runs against batch month − 1.
   Redefining the option would have contradicted `EngineHealthService`,
   `EngineStatusService::lastComputedPeriod()` and every recorded `payout.monthly` period.
3. **`compensation:monthly-payout-close` is now the only unattended path to a monthly batch** — it
   passes `OpenMonthGuard::overrideFor()`. Any future caller of `payout:monthly-run` for the live
   month must do the same, deliberately.
4. **The recompute replay lifts three guards, all narrow and documented**: the cut-off's evaluate
   guard, the open-period refusal (via `overrideFor`, evaluated at the instant being simulated), and
   the monthly batch's completion gate. Without them a replay aborts after the wipe.
5. **Follow-up (out of remit):** a consumed purchase-offer grant deleted by a windowed recompute is
   re-granted while the order that consumed it survives — see F07 above.
6. Unrelated failures seen while working and confirmed not from this batch: `PayoutServiceTest` /
   `PayoutBankDecryptionTest` monthly-batch cases (B3's F48 `earnings_through` work in progress) and,
   briefly, `AdminEngineRunsControllerTest` (B1's F83/F85, green once they committed).
