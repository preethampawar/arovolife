# B10 — Self-service bank details (F70 + F28)

Client decision Q4 (2026-09-11): distributors get their own **Bank details**
page — account number typed twice, IFSC, beneficiary name, OTP-gated, audited.

## F70 — fixed

A distributor who skipped the wizard's optional bank step (bank is optional at
registration, `ProfileController::update()` rejects bank input, and the only
writers were `RegistrationService` and the admin distributor edit screen) sat on
a `no_bank_account` payout hold indefinitely. **My profile → Bank details** is
the missing path.

**Flow.** `GET /profile/bank` shows what is on file (masked account `••••NNNN`,
IFSC, bank, account holder) and the form. `POST /profile/bank` validates through
`BankDetailsRequest`, encrypts, and issues an OTP — nothing is written yet.
`POST /profile/bank/otp` verifies the emailed code and only then writes the
distributor row; `POST /profile/bank/otp/resend` re-sends (3 per 10 min, 30-second
UI cooldown). All four routes sit inside the existing `auth` group with the same
throttles the contact-change routes use, and every action requires a distributor
record (403 for staff).

The OTP flow is the reusable `Shared\Otp\OtpService` — the same `issue / verify /
peek` calls, the same `OtpCodeNotification`, the same modal markup as the
mobile/email change, under a new purpose `bank_details_change`.

**Validation** (mirrors the wizard's bank step so a number accepted at signup is
accepted here): account number 9–18 digits, digits only, `confirmed` against a
re-typed box (paste disabled on the second box); IFSC `^[A-Z]{4}0[A-Z0-9]{6}$`,
upper-cased before validation; beneficiary name required, defaulting to the
user's full name; bank name optional free text (no IFSC lookup exists in the
codebase, so it is not derived).

**PII.** The account number and the beneficiary name are `PiiCrypter` ciphertext
— the same encrypter the registration wizard and the admin edit screen use.
While the code is pending, the OTP payload carries the **ciphertext**, never the
plaintext: that payload is cached (Redis in production) and a raw account number
has no business being there. Only the last 4 digits ever leave the server — page,
audit row and email alike.

**Audit.** `distributor.bank_details_updated` (subject `distributor`), details =
IFSC, bank name, `account_last4`, `via: self_service_otp`; `before_hash` /
`after_hash` are `AuditLog::digest()` raw bytes over the *masked* state
(`ifsc|bank_name|last4|beneficiary-present`) — digesting the account number
itself would be a digest of a 9–18 digit number anyone can brute-force. Issuing
a code also writes `distributor.bank_details_otp_sent`.

**Notification.** `BankDetailsUpdatedNotification` (`mail` + `database`, queued),
the "was this you?" receipt carrying last-4 + IFSC and what to do if it was not.

**Payout hold.** Nothing is called, deliberately: holds are re-read from live
state when a batch is (re-)run and again at approval
(`PayoutService::releaseClearedHolds()`, private, QA F93), so a
`no_bank_account` line releases itself on the next batch touch. `PayoutService`
was not edited (B3 owns it); the controller only calls the existing public
`bankLast4ForDistributor()`. BANK-08 proves the release end-to-end.

**Surfaces.** Profile bank card now shows the account holder and an "Update bank
details →" link, and the page's "locked" note no longer claims bank is
admin-only. The wallet page shows an amber banner linking to the page whenever
there is no account on file or a line is held `no_bank_account`.

**Help docs.** `payout-operations.md` — the "bank details are wrong" section now
names both paths and prefers the distributor's own; `no_bank_account` status row
updated. `compensation.md` — the held-line paragraph says where they add them.

## F28 — fixed

`distributors.bank_beneficiary_name_enc` added — `VARBINARY(512) NULL` on MySQL
(same shape as `bank_account_enc`), PiiCrypter ciphertext, in `$fillable` and
`$hidden`. Named exactly as B9's bank-upload export expects. A plain
`bank_name VARCHAR(120) NULL` was added alongside for the optional bank-name
field. The migration is forward-only and idempotent (`hasColumn` guards) and was
verified on both drivers.
