## F74 — malware-scan switch — fixed

Commit `08478b31` — `security(uploads): switch malware scanning off where the client runs no scanner`

Files:
- `app/config/uploads.php` (new) — `malware_scan` from `CLAMAV_ENABLED`, default ON
- `app/app/Modules/Shared/Http/Rules/ScannedForMalware.php` — skip + warn when the switch is an explicit `false`
- `app/.env.example` — `CLAMAV_ENABLED` (+ the three `CLAMAV_*` keys that were never documented there)
- `docs/compliance/risk-register.md` — R-83
- `app/tests/Feature/Security/MalwareScanningTest.php` — AVS-07, AVS-08

What changed: the scan is skipped only when `config('uploads.malware_scan') === false`. A missing or null value reads as "scan", so an environment that never sets the switch keeps the old fail-closed behaviour — that is AVS-08, and it is the case that would otherwise turn a kill switch into a silent hole. The scanning code is untouched; an infected file and an unavailable scanner both still refuse whenever scanning is on. Each skipped file writes `Log::warning('uploads.scan_skipped')` with user id, field path, size and a SHA-256 of the bytes; the client-supplied file name is deliberately absent and AVS-07 asserts it.

Tests: `MalwareScanningTest` 8 passed (SQLite). No schema touched, so no MySQL run needed.

Follow-up (ops, not code): staging and production need `CLAMAV_ENABLED=false` in `.env` at deploy time, or uploads keep failing there. R-83 says to revisit at the Phase 12 hardening gate.

## F71 — withdrawal flow for an account with no consent rows — fixed

Commit `9cc22b35` — `compliance(consent): treat a missing consent row as live consent, not a withdrawn one`

Files:
- `app/app/Modules/Consent/Services/WithdrawConsent.php` — `hasLiveConsent()` + the idempotency guard in `execute()`
- `app/app/Modules/Consent/Http/Controllers/ConsentWithdrawalController.php` — asks before withdrawing instead of reading the answer out of a row count
- `app/resources/views/consent/withdraw.blade.php` — empty-state for "What you consented to"
- `app/tests/Modules/Consent/ConsentWithdrawalTest.php` — CWD-09, CWD-10, CWD-11

What changed: a missing row is live consent. The flow closes only on an explicit withdrawal — a `withdrawn_at` stamp, or the `consent_withdrawn` closure the service itself writes, which is the only trace a withdrawal can leave on an account that had no rows to stamp. A zero-row withdrawal terminates and audits normally (`consents_withdrawn: 0`), fabricates no acceptance row, and a second submission is still a no-op with no second `DistributorTerminated`.

One case the old code also got wrong and the new rule fixes: a distributor with some rows withdrawn and some live keeps the flow, because a live row wins over a withdrawn one.

Tests: `ConsentWithdrawalTest` 11 passed (SQLite). No schema touched.

## F72 — agreements registry + "My consents & agreements" page — fixed

Commit `bfab164f` — `compliance(consent): give distributors their consent record and backfill the agreements registry`

Files:
- `app/app/Modules/Consent/Console/Commands/BackfillAgreementsCommand.php` (new) — `consent:backfill-agreements`
- `app/app/Modules/Consent/ConsentServiceProvider.php` — registers it (module commands are not auto-discovered)
- `app/app/Modules/Consent/Http/Controllers/ConsentRecordController.php` (new)
- `app/resources/views/consent/record.blade.php` (new)
- `app/app/Modules/Consent/Models/Agreement.php` — `@property` block (phpstan)
- `app/routes/web.php` — `GET /profile/consents` → `consent.record`
- `app/resources/views/profile/show.blade.php` — link in the "Your data and consent" card
- `app/tests/Modules/Consent/ConsentRecordTest.php` (new) — CR-01 … CR-09

What `agreements` is for (data-model.md §agreements): the document side of the consent record — one row per version of each of the four documents, `pdf_hash` BINARY(32) NOT NULL, `effective_from`, and `supersedes_id` chaining versions. `consents` is the person side. With the registry empty the platform could say someone accepted `tnc` `1.0.0` and could not say what `1.0.0` was.

Backfill: per (document_type, document_version), the hash and `accepted_at` of the **earliest** acceptance, then the supersession chain per type in effective order. Inserts only what is missing, rewrites only a wrong link — safe in a deploy script with no "has this run yet" flag (CR-07 runs it three times and compares every field). A `--dry-run` flag reports without writing. Two distinct hashes under one version string are warned about and the earliest is registered (CR-09) — the registry holds one hash per version, and that drift is exactly what versioned consent exists to catch. A version whose earliest acceptance has no hash is left out rather than given a guessed one.

Chose a command over a migration: it reads rows a migration cannot assume exist yet, and a registry that drifts wants re-running rather than editing.

Page: the distributor's own rows only, read-only — document title (taken from the published `content_pages` row, so it names each document the way the document names itself), the version **as recorded** rather than the version published today, accepted at, the acceptance IP (IT Act §10A, shown only to the person it belongs to), in force / withdrawn, each linked to the published page, with the withdrawal route beside it. An account with no rows gets a plain statement that the acceptance was not written down, not an empty table — "you consented to nothing" and "we did not record it" are different claims and only one is true.

Tests: `ConsentRecordTest` 9 passed on SQLite **and** on MySQL (`arovolife_test` in the container) — the table has a BINARY(32) NOT NULL column, an enum and a unique index, so the MySQL run is the one that counts. `tests/Modules/Consent` 21 passed; `ScheduledCommandsAreRegisteredTest`, `Profile*` and `PublicCopyAuditTest` green.

Deploy step: run `php artisan consent:backfill-agreements` on staging and production after this branch deploys (it is not wired into a migration by design). `--dry-run` first if you want the report.
