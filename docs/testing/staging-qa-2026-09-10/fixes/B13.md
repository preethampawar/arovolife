# B13 — F108: before/after digests on every admin, KYC and settings mutation

Client decision Q16: **YES — one sweep.** CLAUDE.md: "any admin action, any KYC
change, any settings change → `audit_log` entry with before/after hashes".
Staging: 19 of 3,235 rows carried a `before_hash`.

`row_hash`/`prev_hash` were already automatic (`AuditLog::booted()` links every
new row); the 1,126-of-3,235 figure is pre-chain history, not a live hole. So
this batch is about `before_hash` / `after_hash` only.

## Shared helper

`app/app/Modules/Compliance/Support/AuditDigests.php` — the single helper every
site now uses.

- `AuditDigests::of(Model|array|string|null $state): ?string` — raw 32 bytes via
  `AuditLog::digest()`, never hex. `null` in → `null` out, so a create stores
  `before_hash` NULL rather than the digest of nothing.
- `AuditDigests::snapshot(Model $model, array $only = []): array` — the model's
  attributes, `$only`-pinned where an action governs named fields.
- Canonical: keys sorted recursively, every scalar normalised to its string form
  (a model just written holds ints and Carbons where the same row read back
  holds strings — without this an untouched column would move the digest),
  `updated_at` dropped.
- PII: identity-number attributes (`pan*`, `aadhaar*`, `account_number`,
  `bank_account`) digest in their masked last-4 form, exactly as B10's
  self-service bank audit; credentials and `*_enc` ciphertext collapse to `set`.
  A digest must not become a lookup oracle over a PAN-sized space.

Tests: `app/tests/Modules/Compliance/AuditDigestsTest.php` (AD-01..AD-09).

### Rules applied at each site
- **Mutation** — snapshot before, snapshot after, digest both.
- **Create** — `before_hash` NULL, `after_hash` the new row.
- **Delete** — `before_hash` the row, `after_hash` NULL (`$model->exists` is
  already false after a delete, so the shared `audit()` helpers derive it).
- **Read / export / trigger / refusal** — nothing moves, so the row either
  carries the *same* digest both sides (a document view, a self-approval
  refusal, a force-payout request) or a NULL before with an after over the
  payload that left the building (an export, a queued engine run). Every such
  site carries a one-line comment saying which and why.

### Deliberately out of scope
Scheduler-authored notice rows — `compensation.monthly_close.in_flight`,
`.aborted`, `compensation.monthly_payout_close.refused`, `PrematureFreezeAlert`,
the Razorpay dispatch/webhook jobs, the purge commands. They record that an
engine did *not* do something; they are not admin, KYC or settings mutations.
Registration, login and order-lifecycle rows are likewise untouched.
`ApproveKycSubmission::purgeIdNumbersAndFiles()` was not edited (F107 pending) —
the purge still shows up in `admin.kyc.approved`'s after digest, because the
distributor rows it rewrites are part of the digested state.

## PII handling
Identity-number attributes (`pan*`, `aadhaar*`, `account_number`,
`bank_account`) reach the digest only as `****` + last 4; a value already four
characters long (`pan_last4`) is kept as-is, since that is the masked form the
column holds in plaintext and collapsing it would make a before and an after
identical. Credentials (`password`, `token`, `secret`, `otp`, `mfa`) and any
`*_enc` ciphertext collapse to `set`. Password changes digest `password_set_at`
instead — the stamp moves on every set and leaks nothing.

Binary columns (`pan_hash`, `checksum_sha256`) are hexed before encoding: an
uncaught `JsonException` inside an audit write would have been an admin action
failing because of its own audit row. Caught by `AdminKycReviewTest` during the
sweep, fixed in the helper, pinned by AD-10.
