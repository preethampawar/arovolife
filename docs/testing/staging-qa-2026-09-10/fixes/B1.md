# B1 — Engine-run observability

Branch `fix/staging-qa-2026-09-10`.

## F81 — fixed

Failed engine runs recorded no reason: `RecordEngineRun::finished()` only wrote a
status, and `EngineRunService::finalise()` then overwrote `error` with the null it
holds whenever `Artisan::call` returns a non-zero exit code without throwing.

- `app/app/Modules/Compensation/Support/EngineRunContext.php` — new outcome channel
  (`noteSkipped()` / `noteFailed()` / `takeOutcome()`), keyed by the active run id so a
  nested command cannot land its note on its parent's row; cleared by `reset()`.
- `app/app/Modules/Compensation/Listeners/RecordEngineRun.php` — consumes the note and
  writes it to `error` + `summary.reason`; a non-zero exit with no note still writes an
  `error` naming the exit code and pointing at the application log.
- `app/app/Modules/Compensation/Services/EngineRunService.php` — `error` is now
  `$error ?? $run->error`, so the listener's reason survives finalisation.

Tests (`app/tests/Modules/Compensation/EngineRunRecorderTest.php`):
`records the reason on a failed run that named none`,
`keeps the engine declared reason when the run is closed out by the run service`.

Commit `0d48e60b`.

## F43 / F50 / F39 — fixed (one change)

Deliberate refusals are recorded `skipped` with their reason, not `failed` with
`error NULL`, matching the existing flag-off=skipped rule. The digest reads
`unresolvedFailures()` (status `failed` only), so refusals stop being reported for
thirty days without touching `EngineStatusService`.

- `GsbWeeklyPayoutCommand` — non-Tuesday refusal → `noteSkipped()`; the exception
  catch → `noteFailed()`.
- `MonthlyCloseCommand::abort()` — stage `preflight` → `noteSkipped()`; a broken step
  → `noteFailed()` with the step message.
- `MonthlyPayoutCloseCommand::refuse()` → `noteSkipped()`; the crash catch →
  `noteFailed()`.

Tests: `records a deliberate refusal as skipped, with the reason, not as a failure`
(EngineRunRecorderTest), `records a preflight refusal as skipped with the reason, not
as a bare failure` + `records a broken step as a failure carrying the step message`
(MonthlyCloseCommandTest), `records the refusal as a skipped run carrying its reason`
(MonthlyPayoutCloseCommandTest), `does not report a deliberate refusal as a failure`
(EngineHealthDigestTest).

Commit `0d48e60b`.

Follow-up (not a regression, worth a decision): both close commands are orchestrators,
which `EngineHealthService::missing()` excludes, so a refusal is now silent in the
digest — the crediting engine actually at fault is still reported in its own right,
which is the item the reader has to act on. If the client wants the close itself
surfaced, it needs a fourth digest section for `skipped` refusals rather than a return
to `failed`.

## F12 — fixed

`PropagateGroupBvJob` / `ReverseGroupBvJob` declared `$tries = 3`, overriding the
compensation worker's `--tries=1` (ADR-0011). Both are now `$tries = 1`; the now-dead
`$backoff = 60` went with them. The propagation's own `DB::transaction(..., 3)` deadlock
retry is untouched — that is the retry that was doing real work.

- `app/app/Modules/Compensation/Jobs/PropagateGroupBvJob.php`
- `app/app/Modules/Compensation/Jobs/ReverseGroupBvJob.php`
- Test: `leaves the group-BV jobs on the single attempt ADR-0011 mandates`
  (`app/tests/Feature/QueueRoutingTest.php`).

No risk-register entry needed: the deviation is removed, not kept.
`ProcessRazorpayPayoutWebhookJob` keeps `$tries = 3` deliberately — it talks to an
external HTTP endpoint, where a retry is the recovery.

Commit `30d87843`.

## F121 — fixed

`grievance:sla-sweep` now logs `grievance.sla_sweep.completed` with tickets checked,

## F30 (design half) — fixed

New `PrematureFreezeAlert::kept()` writes one `compensation.premature_freeze_kept`
audit row per kept pool (deduplicated on subject, because every later run for the period
re-detects the same condition), called from all five keep sites: GSB daily, MSB daily,
GBB monthly, Rank monthly, Fortune monthly. Audit, not `engine_runs`: the run that finds
a kept freeze succeeds, so there is no failed row for the signal to hang off.

`EngineHealthService` reads those rows over the same 30-day window and reports them as a
fourth digest section — "Periods priced against a pool frozen too early" — whose remedy
steps say explicitly NOT to re-run the engine (it would price against the same snapshot)
and to escalate the same day. `EngineHealthReport::total()` counts them, so the digest
sends on a day whose only problem is a kept freeze.

Files: `PrematureFreezeAlert`, the five pool services, `EngineHealthService`,
`EngineHealthReport`, `EngineHealthDigestNotification`, `EngineHealthDigestCommand`,
`resources/help/compensation.md` (new item **F** plus the refusal note on failed runs).
Tests: `reports a pool the self-heal had to keep after a premature freeze`,
`records a kept premature freeze once, however many runs re-detect it`
(EngineHealthDigestTest), plus an audit assertion on the existing
`keeps a premature pool once results were priced against it` (GsbDailyPoolServiceTest).

Commit `de602350`. Verified on MySQL as well as SQLite.

The data half (re-pricing 2026-09-05) stays with F10's windowed recompute.
