## Defects

| # | Sev | Defect |
|---|-----|--------|
| **D1** | **Low (UX)** | **`/profile` shows no bank last-4 — the mask is a literal, meaningless `••••`.** `resources/views/profile/show.blade.php:71` hardcodes `value="Account on file ••••  ·  IFSC {{ $distributor->bank_ifsc }}"`; there is no `pan_masked`-style accessor in the string. The distributor cannot tell *which* account is on file, while the payout batch export and `PayoutService::bankLast4ForDistributor()` both know it is `…0002`. The help tip ("your account number is encrypted and never shown; only the branch IFSC is displayed") makes this deliberate, but a real last-4 is the normal, safe affordance and every other surface uses one. **Expected:** `Account on file ••••0002 · IFSC HDFC0000001`. **Actual:** `Account on file •••• · IFSC HDFC0000001`. |
| **D2** | **High (design/ops)** | **A registered distributor has no way to add or change bank details.** Bank is *optional* at registration (`handleBank()`: "If both fields are blank the step is skipped and the distributor row is created with NULL bank columns"), and its own comment says *"they can add bank later from their dashboard"* — **no such surface exists.** `grep -n "bank" routes/web.php` returns only the three wizard lines; the only writers of `bank_account_enc` are `RegistrationService`, `AdminDistributorController` / `AdminDistributorEditController` and the seeders. So anyone who skips the step is stuck on payout status `no_bank_account` **forever** until an admin edits their row by hand. Consistent with staging: only 2 of 317 distributors have bank details, and both were written by T01. **Repro:** log in as any distributor → there is no bank link on `/profile`, in the sidebar, or anywhere else; `/register/kyc/bank` 302s to `/dashboard`. Cross-refs F28 / F44. |
| **D3** | **Low (copy)** | **Raw field name leaks into user-facing validation copy: "The new_password is too easy to guess" / "The new_password has appeared in known data breaches."** Cause: the closures interpolate the raw attribute instead of using Laravel's `:attribute` placeholder — `StrongPassword.php:31` `$fail("The {$attribute} is too easy to guess…")` and `NotPwned.php:68` `$fail("The {$attribute} has appeared in known data breaches…")`. Both rules are also used by the registration wizard and the password-reset flow, so the same string appears there. **Expected:** "Your new password is too easy to guess…". |
| **D4** | **Low (UI)** | **Duplicated title on `/dashboard/documents`: `My documents — arovolife — arovolife`** (the view's `@section('title')` already contains the brand, which the layout then appends again). |
| **D5** | **Medium (compliance/data)** | **No document-and-consent record is retrievable by the distributor, and the `agreements` registry is empty.** (a) There is no page listing the four consented documents with their versions — `/dashboard/documents` is the KYC uploader, and `/profile` only links the Privacy Policy. (b) `agreements` (the table holding `version`, `pdf_hash`, `effective_from`, `supersedes_id`) has **0 rows on staging** while 1,144 `consents` rows point at version strings in two incompatible schemes (`1.0.0` and `2026-08-30`). A consent recorded against a version with no immutable, hashed document behind it cannot be evidenced if a distributor later disputes what they accepted (T&C §12 amendment-by-notice makes this live). |
| **D6** | **Low (copy, confirms F68)** | Membership-card back uses employee wording on an independent contractor's credential — *"displayed at all times while in office"*, *"bring this to HR's notice immediately"* — contradicting DSA §5 printed on the sibling page. |
| **D7** | **Low (copy)** | **PAN mask on the Direct Seller Application is 11 characters: `XXXXXX8994X`.** `resources/views/membership/direct-seller-application.blade.php:57` builds `'XXXXXX'.$distributor->pan_last4.'X'`. A PAN is 10 characters. `/profile` renders the same value as `XXXXXX8994` via `Distributor::panMasked()` (`str_repeat('X', 6).$this->pan_last4`). The two surfaces disagree, on a document a distributor may hand to a bank. Also on that page: the agreement text still contains the literal placeholder **"as amended from time to time which shall be notified on the website (web address)"**. |
| **D8** | **Low (data, launch-relevant)** | **The 31 reserved company accounts have a zero-day cooling-off window** — `DATEDIFF(cooling_off_end_at, created_at)` is **0** for distributor ids 1–31 and **30** for ids 32–318. The consequence is visible in user-facing legal copy: the Direct Seller Application prints "Cooling-off ends 04 Jul 2026" against a registration date of 04 Jul 2026, and `/cooling-off` says "The **30-day** window expired on 04 Jul 2026". Only the seeder is affected (the real registration path is correct), but the memory note *"reserved accounts accrue, assigned to leaders later"* means these rows are expected to end up owned by real people carrying a statutorily wrong document. |
| **D9** | **Medium (compliance/UX)** | **`/profile/withdraw-consent` tells a fully active distributor "Your consent has already been withdrawn."** `WithdrawConsent::hasLiveConsent()` is `consents.where(distributor_id).whereNull('withdrawn_at')->exists()` — it cannot distinguish *withdrawn* from *never recorded*. For user 3 (`status=active`, `closure_type=NULL`, 0 consent rows) the view takes the `! $hasLiveConsent` branch, states something untrue, and hides the entire §6 flow — consequences, the document list, and the withdrawal control. **Expected:** the no-consent-on-file case should say so and route to support, not assert a withdrawal that never happened. Affects the 31 reserved accounts today. |
| **D10** | **Low (UI)** | At a ~422 px viewport the `/profile` bank field clips its own value (`IFSC HDFC000000`, final character cut) with no scroll or wrap affordance. Desktop is clean. |

Minor, but the OTP panel is a surprise. | **D12** | **Info (pre-existing, out of T24 scope)** | `audit_log.before_hash` / `after_hash` are populated on only **18 of 3,199** rows (`row_hash` on 1,092), including both `profile.updated` rows written by this task, although CLAUDE.md requires "`audit_log` entry with before/after hashes".
