# T41 — Security spot-check: endpoints added or changed since 2026-09-03

Date: 2026-09-10 · Reviewer: security-auditor · Scope: `git log --since=2026-09-03`
over `app/routes` + `app/app/Modules/*/Http` (messaging, announcements, FAQ,
content pages, payments/Razorpay, payout settings, engine runs, distributor
communications wiring).

Method: read-only source review + one read-only SSH read of the staging `.env`
safety flags. **Unauthenticated HTTP probes against staging were NOT run** — the
`curl` permission was denied by the permission system on every attempt, and I did
not route the probes through SSH to work around that decision. Every HTTP-level
claim below is therefore derived from route/middleware/controller source, and the
three items marked *unverified-on-wire* need a re-run with curl approved.

## Verdict

**SECURITY: FAIL** — one High finding blocks: `/messages/{user}` discloses any
user's name to any authenticated member, which defeats the audience restriction
shipped in the same commit (f5e808df) and exceeds the R-65 subtree scoping of
hard rule 3.

Everything else in scope is clean or Medium/Low. No Critical findings. The
payments series (41fdee4e…f091bdab) and the recompute gate (20b4a0f6) came back
clean and are, in this reviewer's opinion, the strongest code in the window.

## Clean

1. **Messaging authorization (read).** `index()` scopes strictly to the viewer's own pairs; `threadBetween` (`Models/Message.php:69`) cannot return a third party's thread — A cannot read B's conversations with C. F-1 is about the *name* on the page, not the messages.
2. **Messaging audience/rate limits/block list.** All guards in `MessageService`, not the controller, so the tree-card modal path is covered too. Defaults: audience `downline_upline` via `TeamStatsService::sharesLineage()`, 60 sends/hour/sender, 20/day/sender/recipient, 4000-char body (`Services/MessagingSettingsService.php:33-40`); an unrecognised stored audience value falls back to the restrictive one (`:50`). Refused sends do not consume quota (POL-07). Block list one-directional, staff unblockable, and a block against staff is never consulted (`MessageService.php:180`).
3. **PII guard coverage.** `NoRawGovernmentId` is applied to every free-text field in the window: message body (unconditional, no setting — `MessageService.php:213`), report reason (`MessageController.php:255`), reviewer note (`Admin/AdminMessageReportController.php:98`), announcement title+body (`AdminAnnouncementController.php:186`). Aadhaar candidates are Verhoeff-checked before rejection (POL-15). No attachment path exists in messaging — nothing to scan.
4. **Report flow.** Recipient-only (`MessageController.php:250`), `firstOrCreate` on a unique index so the queue cannot be inflated, categories `Rule::in`-bounded. Moderation queue is `can:messaging.moderate` = operations + compliance, admin-finance excluded (`database/seeders/RolesAndPermissionsSeeder.php:86`); the reviewer sees the reported message ±3 only (`AdminMessageReportController.php:39,131`) and every open writes an audit row (`:76`, tested at POL-14).
5. **Mass assignment.** `Message` (`Models/Message.php:26`) and `MessageReport` (`:49`) carry explicit `$fillable`; announcement create rebuilds a whitelisted array and sets `status`/`created_by_user_id` server-side (`AdminAnnouncementController.php:70`); content pages go through a FormRequest.
6. **Stored XSS.** Announcement bodies are escaped — `resources/views/announcements/show.blade.php:14` documents the refusal to use `{!! !!}`. The one raw echo, `resources/views/content/show.blade.php:40`, is fed only by bodies passed through **HTMLPurifier** (`mews/purifier`) on both write paths (`AdminContentPageController.php:37,75,117`). No unsanitised admin HTML reaches a view.
7. **Unpublished-page leakage / the FaqSlugBypass scratch test.** Closed and now covered by a real test: `PublicContentPageController::show()` (`.../Public/PublicContentPageController.php:27`) filters `status = published` **and** excludes `type = faq`; `FaqLibraryTest` FAQ-07 asserts a published FAQ entry is not served by `/p/{slug}`, FAQ-04 that drafts are not listed, FAQ-01/02 that the surface 404s (not 403s) while the flag is off or members-only is on.
8. **Publish-one-at-a-time.** Enforced by an artisan command with an explicit slug allow-list (`PublishContentPageCommand`, tested), not by an HTTP endpoint — nothing to bypass over the wire.
9. **Announcement audience is enforced server-side.** `AnnouncementController::show()` re-runs the audience query and 404s on a guessed id (`.../AnnouncementController.php:47-53`), tested at ANN-11.
10. **Razorpay webhook (inbound).** HMAC-SHA256 over the raw body with `hash_equals` (`Services/RazorpayClient.php:215`); unconfigured gateway ⇒ 404, not a permissive path (`RazorpayWebhookController.php:44`); dedupe on `x-razorpay-event-id` with a body-digest fallback and a `UniqueConstraintViolationException` ⇒ 200 no-op; store-then-queue so a slow apply cannot induce retries; CSRF exemption is narrow and justified (`bootstrap/app.php:43-47`); `throttle:600,1`.
11. **Payout webhook.** Same signature/dedupe model, plus a `JsonException` catch and a deliberate 200-on-unverified to avoid a redelivery storm; only an 8-char prefix of the rejected signature is logged (`RazorpayPayoutWebhookController.php:47-56`).
12. **payment_events scrubbing.** `RazorpayPayloadScrubber` is an **allow-list** — new gateway fields are dropped by default; `card.name`, `email`, `contact`, `vpa`, `bank_account`, `token_id`, `customer_id` never stored; `card.last4`/network kept (SAQ-A safe). Applied before `payment_events`, `payment_intents.raw_payload` and the `payments` log channel.
13. **Payments screen separation of duties.** Read = `audit.read`; every money-moving action (`refunds/{refund}/retry|settle`, `orders/{order}/settle|invoice`, `{intent}/sync`) additionally `can:finance.record` (`app/routes/web.php:406-418`), each with an `AuditLog::create` carrying before/after digests. `returns.receive` is deliberately held by operations, never finance.
14. **Payout settings / stealth role.** Route group `role:developer`, nav item hidden, credentials never rendered (only presence), Spatie exception messages carry no role or permission names. The settings registry enforces ownership server-side with a **404** (not 403) for developer-owned keys and for keys whose feature flag is off, so probing cannot confirm that the key or the role exists (`AdminSettingsController.php:1528-1538`, `ownerForKey()` at `:1319`).
15. **Recompute in-flight refusal is server-side.** Cache lock + heartbeat tiebreaker in the controller, before dispatch (`AdminEngineRunsController.php:202`); the partial-engine selection requires an explicit `accepted` acknowledgement; the manual `trigger` endpoint refuses scheduler-only engines and flag-off engines server-side (`:429,438`) and writes an audit row naming the actor, the reason and the planned chain before dispatching (`:448`).
16. **Audit coverage on the new admin actions (b14001da).** Announcement create/update/transition, content page create/update/archive, report open/review, settings update and feature-flag toggle (`AdminFeatureFlagController.php:251`) all write `audit_log` rows. No new admin action in the window is missing one.
17. **Security headers / transport.** `SecurityHeaders` middleware is appended to the whole `web` group: CSP with `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, plus `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`; HSTS `max-age=31536000; includeSubDomains` on TLS, with `trustProxies` configured so `$request->secure()` is true behind the Cloudways LB. CSP still allows `'unsafe-inline'` for script — a known, documented limitation (inline Blade handlers), tracked, not a new finding. `APP_DEBUG=false` on staging. *(Header presence on the wire is unverified — curl denied.)*
