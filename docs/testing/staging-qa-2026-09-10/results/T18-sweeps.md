## Defects

**D1 (Medium, code) — Manual-NEFT reconcile has no amount-match validation, contrary to the shipping commit's own description.**
`app/Modules/Compensation/Services/PayoutReconciliationService::import()` (commit `253ed21c`) only reads ADN, Status, UTR and Reason columns from the bank response CSV. It never reads or compares an amount column against `payout_line_items.net_transferred_paise`. The commit message for `253ed21c` explicitly claims "PayoutReconciliationService: ... detects amount mismatch" — the shipped code does not do this. A bank file with two rows' amounts transposed (same ADNs, swapped values) would import silently as `transferred` for both lines with no discrepancy ever raised.
Repro: read `app/Modules/Compensation/Services/PayoutReconciliationService.php` lines 26-183 — `ADN_HEADERS`/`UTR_HEADERS`/`STATUS_HEADERS`/`REASON_HEADERS` are the only recognised columns; no `AMOUNT_HEADERS` constant or amount comparison exists anywhere in the class.
Expected: import should compare a parsed amount column (if present) to `net_transferred_paise` and report/skip a mismatch rather than trusting the status column blindly.

**D2 (Medium, code) — Manual-NEFT reconcile has no duplicate-UTR guard.**
Nothing in `PayoutReconciliationService::import()` checks whether a UTR being written already exists on another line item (same import, a prior import, or a different batch), and `payout_line_items.utr_number` carries no unique index (`SHOW CREATE TABLE` on staging: only `uniq_payout_line(payout_batch_id, distributor_id)`). A bank file with a duplicated/typo'd UTR (e.g. copy-paste error) would mark two distinct distributors "transferred" against the same bank reference with no warning.
Expected: either a DB unique constraint on `utr_number` (scoped appropriately) or an application-level duplicate check that reports it in the import summary like `unmatched`/`skipped` do.

**D3 (Low, code, not exploitable today) — `orders:expire-unpaid`'s "final gateway check" doesn't cover stub-gateway orders at all.**
`ExpireUnpaidOrdersCommand::expire()` only looks up `PaymentIntent::where('gateway', PaymentIntent::GATEWAY_RAZORPAY)`. On a stub-only environment (staging today, and any UAT/demo build) this means the command's described safety net — "ask the gateway one more time before cancelling" — silently does nothing; it goes straight to `$orders->cancel()`. Currently harmless only because `PaymentConfirmationService::confirmStub()` commits the intent-capture and the order-settle in one DB transaction, so the two states can't be observed apart. If that invariant is ever weakened, this sweeper has no independent check to catch it for stub orders.
Expected: either scope the query to check `PaymentIntent::whereIn('gateway', [RAZORPAY, STUB])`, or document explicitly that the check is razorpay-only by design.
