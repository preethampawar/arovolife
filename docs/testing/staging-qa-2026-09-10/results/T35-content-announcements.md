## Findings

### #1 — `NoIncomeProjection` is a literal substring match, so a plain income promise passes (severity: **High**, compliance — hard rule 3 / DSR 2021 Rule 5(1)(d))
`app/Modules/Shared/Rules/NoIncomeProjection.php` matches a fixed `BANNED_PHRASES` list as lowercased substrings. The body **"You can earn ₹50,000 per month guaranteed with arovolife."** was accepted and persisted to `content_pages` id 9 (check 7): it contains neither `earn per month` (the amount splits the phrase) nor `guaranteed income` (the word order is "month guaranteed"). The rule is wired correctly and fires with a clear message when a listed phrase is literally present (check 9, positive control passed) — the gap is the phrase list, and the same list guards announcements, which reach every distributor at once. A number-and-period pattern (`earn … ₹N … per month/day/week`) would have caught this one. Repro: create or edit any typed content page or announcement with that sentence as the body.

### #2 — Blank `sort_order` returns HTTP 500 instead of a validation message (severity: **Medium**)
Leaving Sort order empty on `/admin/content/create` reaches the DB insert and dies on `SQLSTATE[23000]: Integrity constraint violation: 1048 Column 'sort_order' cannot be null` (laravel.log, 2026-09-11 01:07:10); the admin sees a Server Error page and loses the form. `sort_order` needs a `nullable`+default or a `required|integer` rule in `ContentPageRequest`. The field is optional-looking in the UI (no `*`), so this is the natural first attempt.

### #3 — The rich-text editor is a hard runtime dependency on a third-party CDN, and fails silently (severity: **Medium**, availability)
`resources/views/admin/content/_form.blade.php` and `resources/views/admin/catalog/products/form.blade.php` load Trix's JS **and** CSS from `unpkg.com` at page render. When unpkg is unreachable for the admin's browser — as it is from this Chrome, while the same URL returns `200, 203260 bytes` from the staging server — `<trix-editor>` is never upgraded: the Body field shows as an empty bordered box with no toolbar, no error, and no console message, and an admin who types nothing into it and saves silently blanks the page body. Everything else on the platform ships through Vite from the app's own origin. Pinning a local copy (or a `window.Trix` check that disables the save button with an explicit message) would remove both the outage dependency and the silent-blank risk.

### #4 — "Publish one at a time" is not implemented for announcements (severity: **Medium**, spec gap — confirm intent before changing anything)
`AdminAnnouncementController::transition()` guards a publish with exactly two checks — the `NoIncomeProjection` re-scan of `title.' '.body`, and `AnnouncementService::canPinAnother()` when the announcement is pinned. There is **no** check for an already-published announcement. Verified live (check 17): announcement 2 published cleanly while announcement 1 was still `published`, with no refusal message and no auto-archive of the first, and the distributor-facing `/announcements` listed both at once. The only exclusivity rule that exists is the **pin limit** (`announcements.pin_limit`, default 3 — so up to three pinned at once, and a fourth pin is refused rather than silently unpinning another). If one-live-at-a-time is genuinely the intended policy it is unbuilt; if the intended rule was always the pin limit, the QA plan's wording is what needs correcting. Flagged rather than assumed.

### #5 — Publishing a content page is audit-logged as `content_page.updated` (severity: **Low**)
Moving page 9 draft → published wrote audit **3240 `content_page.updated`**, indistinguishable from a typo fix. Archiving, by contrast, gets its own `content_page.archived` action (3241), and announcements get `announcement.published` (3243/3245). Publication is the moment copy becomes visible to members, so it is the state change most worth being able to find in the audit log by action name.

### #6 — A message report does not identify the two parties (severity: **Medium**)
`admin/messaging/reports/show.blade.php` (lines 77–78) prints only `full_name` for "Reported by" and "Sender". On report 1 both are company reserved accounts, so both fields read "Arovolife Private Limited" and a moderator cannot tell who reported whom, cannot reach either account, and the audit trail of their decision records no party either. Real distributors sharing a common name would hit the same wall. The ADN (and a link to the distributor page, since the header copy tells moderators to apply consequences with "the account tools on the distributor's page") is what this screen is missing.

### #7 — `messaging.moderate` does not exist on staging, so neither operations nor compliance can open the reports queue (severity: **High**, deployment / separation of duties, R-17)
`permissions` on staging holds 12 rows; `messaging.moderate` — the only permission from `RolesAndPermissionsSeeder` that is absent — is not among them, and no `role_has_permissions` row grants it. The routes are gated `can:messaging.moderate`, so `admin-operations` and `admin-compliance`, the two roles the seeder assigns it to and the two intended to staff this queue, are locked out; the queue is reachable only by `admin`/`developer` through the `Gate::before` super-staff bypass. R-17's actual requirement (finance excluded) happens to hold, but by accident of the permission not existing rather than by a grant that excludes finance. Fix is to re-run `RolesAndPermissionsSeeder` on staging — it is `firstOrCreate`/`givePermissionTo` throughout, i.e. strictly additive — and to re-check it as part of the deploy checklist, since a permission added after the last seeder run is invisible until someone tries the page.
