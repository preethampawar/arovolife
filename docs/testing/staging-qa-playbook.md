# Staging QA playbook — full-platform verification (reusable)

First run: 2026-09-10/11 (plan + results in `docs/testing/staging-qa-2026-09-10/`). Written 2026-09-11 at the user's request so the next run starts here instead of re-planning. **Update this file at the end of every run** (section 9 especially).

## 1. What this QA covers and how it is organised

One orchestrator (Fable) plans, launches, monitors and consolidates. Each task is ONE subagent with a brief small enough to stay under ~100k context. Verification tasks run on Opus; data-setup and log sweeps on Sonnet. Sonnet stalled twice on a rich-text form in the first run — use Opus for any task with complex form interaction.

Phases, in the order that worked:

| Phase | Tasks | Runs | Model |
|---|---|---|---|
| 0 Setup (SSH/DB) | T01 QA logins + bank details + KYC for earning accounts; T02 product BV sanity | in parallel | opus / sonnet |
| 1 Engines + schedule (SSH/CLI, no browser) | T10 repurchase, T11 gsb daily cut-off, T12 weekly payout, T13 monthly close, T14 in-flight month audit, T15 monthly payout close, T16 engine-health digest, T17 scheduler/cron/worker audit, T18 sweeps (auto-retry, reconcile, expire-unpaid) | up to 3 in parallel (they only read) | opus (T16–T18 sonnet) |
| 2 Distributor journeys (Chrome) | T20 dashboard, T21 shop→checkout→orders→admin ship/deliver, T22 income pages foot to DB, T23 Genos/team, T24 profile/KYC/bank/tax/card, T25 communications, T26 public site | ONE AT A TIME | opus |
| 3 Admin (Chrome) | T30 engine runs page, T31 compensation reports + I&O + exports, T32 payouts + NEFT + approval, T33 orders/BV ledger/payments/returns, T34 distributors/KYC/audit/flags/settings/help docs, T35 content/announcements/FAQ/message reports, T36 analytics/dormancy/grievances/Arete | ONE AT A TIME | opus (T35/T36 were planned sonnet; use opus) |

Phase 1 can run while phase 2 runs (DB reads vs browser). Never two Chrome tasks at once: the Chrome MCP shares one cookie jar.

## 2. Before launching anything — baseline checks (orchestrator, ~15 min)

1. `git log -1` locally vs deployed commit on the server (`git -C <app path> log -1`), `php artisan migrate:status` shows 0 pending, `php artisan about` (config not cached on staging).
2. Feature flags: read `/admin/feature-flags` state or the `features` (Pennant) table. Note which are OFF — flag-OFF surfaces are expected to be zero-trace.
3. Queue: `QUEUE_CONNECTION` in `.env`; supervisor workers (`ps aux | grep queue:work`) — the worker connection name `redis` is aliased to the database driver in `config/queue.php` (ADR-0011). Push one probe job and confirm it drains; delete only that probe's failed row if it fails.
4. Scheduler: `crontab -l` runs `schedule:run` every minute; `php artisan schedule:list`; `engine_runs` shows the 00:05 / 00:10 rows for the last few days.
5. Data snapshot: distributors count, users by status, orders by status, payout batches, wallet ledger totals, `engine_runs max(id)`, `audit_log max(id)`, `failed_jobs count`. Write these into the plan's Baseline section — every later "foots to DB" check compares against live SQL, but the mutation ledger needs these starting ids.
6. Read the last week's commits (`git log --since`) and turn each user-facing change into at least one check in the relevant task.

## 4. Rules every agent brief must contain

1. Staging only; never `git pull`, edit `.env`, `migrate:fresh`, `recompute-all`, `reset-purchase-data`, `queue:clear`, bulk delete, deploy.
2. Never run a pool-freezing engine for an in-flight period (today / current month). Closed, already-succeeded periods only (idempotent re-runs are fine and prove idempotency — take before/after counts).
3. Record every mutation (table, ids, before → after) under "Mutations" in the result file.
4. Every verdict needs evidence: query + result, or URL + page text. No "looks fine". UI ≠ DB, UI ≠ plan parameters, code ≠ docs → FAIL.
5. Never print full PAN / Aadhaar / bank / OTP values; last-4 only.
6. Browser session rule (adaptive): call `tabs_context_mcp` first; open your own tab. If a STAFF session exists, keep it, impersonate for distributor views, "Stop impersonating" after, never sign out. If no session, sign in yourself and sign out only if you signed in. A leftover DISTRIBUTOR session may be signed out. Record the mode used.
7. Write the result file incrementally (after every check) — agents stall.
8. Reply to the orchestrator with ≤ 25 lines: verdict, numbered findings with severity, mutations.

Result file template:
```
# Txx — <title>
Verdict: PASS | PASS-with-notes | FAIL | BLOCKED
## Session mode
## Checks
| # | Check | Expected | Observed | Evidence | Result |
## Findings (Critical/High/Medium/Low/Info; exact repro; expected vs actual)
## Mutations made on staging (table, ids, before → after)
## Console errors / slowest page
## Notes for the orchestrator (≤ 10 lines)
```

## 5. Seeding needed before a run (what T01 does, plus what the first run lacked)

- Bank details for every distributor that will appear in a payout batch — via `DevBankAccountSeeder`-style PiiCrypter ciphertext, never raw SQL (raw plaintext → every payout `bank_decrypt_failed`).
- KYC active (`users.status='active'`) for the same accounts; at least one pending applicant left for T34 to approve and one to flag.
- At least one paid order to ship/deliver (T21/T33), one delivered order inside the return window (T33 return flow), one unpaid order for `orders:expire-unpaid`.
- One published announcement and one FAQ content page (`type='faq'`) BEFORE T25 — the first run had none, so distributor-side rendering was code-verified only.
- ClamAV reachable (`CLAMAV_HOST`) — without it every upload (distributor requests, grievance evidence, KYC re-upload) is refused and those flows cannot be tested (F74).
- A working outbound mailer or a log/array mailer — staging SMTP rejected during the first run, so "email sent" claims were verified from jobs/logs only.
- Populate `agreements` registry / consents so DPDP record pages have data (F72).
- Closed periods with real numbers for every engine: at least one full closed month with rank/GBB/Fortune/ADC results, one closed week with a payable (not held) payout line so admin-charge/TDS arithmetic can be observed (first run had none — F99).

## 6. Foot-check recipes (SQL the agents used; adapt column names with `show columns`)

- Daily cut-off page vs `gsb_cutoff_results` (rows per date, pool BV) and `wallet_ledger_entries` grouped by engine/entry type for that date; MSB point value = 3% of day BV ÷ total points.
- Weekly payout batch: `payout_line_items` sums (gross, repurchase_deduction, admin_charge, tds, net) per `payout_batch_id`; hold reasons vs `distributors.bank_account_enc`, `users.status`, BV ≥ 3000.
- Monthly engines: `gbb_monthly_pools`, `rank_qualifications`, fortune/adc result tables; index pages read only credited results (F87).
- Income pages: `wallet_ledger_entries` per distributor (exclude `repurchase_deduction` rows from cash totals — F52/F89).
- BV: `bv_ledger_entries` (personal), `group_bv_credits` / `group_bv_daily` (group), reversals in `group_bv_reversals` on refund (originally-credited upline only, ADR-0010).
- Tree counts: everything through `TeamStatsService::scopedQuery()`; compare card stats with closure-table counts.
- Analytics tiles: registrations/users by status, orders, `bv_ledger_entries` sums — remember `@bv()` already divides paise by 100 (F119).
- Grievance SLA: `sla_acknowledgement_at` = created + 48 h, `sla_first_response_at` = +5 working days, `sla_resolution_at` = +30 days.
- Engine runs: `engine_runs` (id, engine_key, period_start, status, trigger, actor_id, summary, error, duration_ms) — `error` is never written today (F81), so failure reasons live only in laravel.log.

## 7. Harness pitfalls hit in the first run (read before launching agents)

- One Chrome session for everyone → serialize browser tasks; DB tasks can overlap.
- Coordinate / `ref` clicks were intermittently inert; agents must drive the element's own handler or submit the form via `javascript_tool` before calling a button dead.
- Trix editor (content pages) loads from unpkg and sometimes never initialises → set the hidden `input[name=body]` via JS.
- Opus session limit (HTTP 429) kills agents mid-run; the harness also kills agents with no progress for 600 s. Always brief "write the result file incrementally", and check the result file + DB for partial mutations before relaunching. `SendMessage` to the same agent id resumes with context intact; if it stalls twice, relaunch fresh on Opus with the state summarised.
- zsh: quote globs in grep (`--include='*.php'`) or pass directories; unquoted `routes/*.php` aborts.
- The Laravel app is under `app/` — the shell cwd drifts between repo root and `app/`; use absolute paths in briefs.
- Never trust an agent's High/Critical without confirming it yourself in code or DB (two of the first run's Highs were downgraded on inspection: F82 was by design, F61 was half wrong).
- Agents must never announce "email sent" from a flash message — check `jobs`, `failed_jobs`, laravel.log or the mail log.

## 8. Cleanup after a run (list, then ask the user before deleting anything)

Every QA mutation is listed under "Mutations" in each `results/Txx-*.md`. First run's residue: QA orders, return/refund rows, grievance tickets, announcements/content page (archived), message report review, KYC approval + flagged doc, approved payout batch, manual engine_runs rows, audit rows. ## 10. Fix phase (added 2026-09-11 after the first fix run)

How the 123 findings were fixed, and what to do differently next time.

- **Plan first, one document.** `fix-plan.md` splits findings into (A) clear-path code batches by module with disjoint file sets, (B) decisions for the user in yes/no form with a one-line explanation and a recommendation, (C) not-code (client/ops/data). The user forwards (B) to the client and returns "Client yes/no" per question; record the answers in the same file.
- **Batches.** 14 batches of 3–11 findings, Opus for logic, Sonnet for copy/report batches; each gets `fixes/IMPLEMENTER-BRIEF.md` + its section of the plan + the F-rows, writes `fixes/<batch>.md` incrementally and ticks the plan. Keep ≤ 8 concurrent: 10 concurrent burned the Opus session limit twice (kills at 12:40 and 17:40 IST); each kill costs a resume round trip. `SendMessage` to the agent id resumes it with context — always resume, never relaunch.
- **Shared working tree = commit races.** Every batch `git add`-ed only its files, but `git commit` commits the whole index, so batches repeatedly swept each other's staged files into their commits (attribution and `Compliance-Review` trailers lost on ~6 commits). Rule for next time: `git add <paths> && git commit -- <paths>` in every brief from the start, or give each batch its own worktree (needs `composer install` + `.env` per worktree, and the MySQL container only mounts the main tree).
- **Full suite.** `php artisan test` dies at the 256 MB default on this suite; run `php -d memory_limit=3G vendor/bin/pest --compact` (SQLite, ~65 s) and the same inside `arovolife-app` with `DB_CONNECTION=mysql DB_DATABASE=arovolife_test` (MySQL). Larastan drifts with every fix (stale baseline entries + Pest `TestCall::actingAs` false positives in new test files): regenerate the baseline at the end, then confirm 0 errors, rather than per batch.
- **Dev DB.** Batches must not run `php artisan migrate` on the dev DB mid-run (they would apply each other's half-written migrations); the orchestrator applies them once at the end inside the container.
- **Decisions that came back from the client (2026-09-11)** are in `staging-qa-2026-09-10/fix-plan.md` §B and drive the next run's expectations: members pay the distributor price; MSB is a deduction source; company centres never earn ADC; maker-checker (`finance.approve`, admin only); NEFT export is a real bank file; self-service bank page; COD off; whole-order returns; guests may browse; several live announcements; helpline 10:00–18:00 Mon–Sat; malware scanning disabled by client decision (R-83); audit digests everywhere.
