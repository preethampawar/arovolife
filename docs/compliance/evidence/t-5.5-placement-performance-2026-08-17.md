# T-5.5 — Placement performance proof

**Date:** 2026-08-17
**Gate:** "1M-row tree, p95 placement ≤ 250 ms"
**Result: PASS** — p95 **1.8 ms**, two orders of magnitude inside the budget.

---

## What was run

```
docker compose exec -e DB_DATABASE=arovolife_perf app \
  php artisan genealogy:benchmark --nodes=1000000 --samples=500
```

`app/Modules/Genealogy/Console/Commands/PlacementBenchmarkCommand.php`.

| Metric | Value |
|---|---|
| Distributors | 1,000,000 |
| Closure rows | 18,951,445 |
| Max depth | 19 |
| Samples | 500 |
| p50 | 0.7 ms |
| p95 | **1.8 ms** |
| p99 | 2.2 ms |
| Budget | 250 ms (p95) |
| Seed time | ~7 min |

A 100,000-node run on the same machine gave p95 0.4 ms over 1,568,946 closure
rows. Ten times the tree moved p95 by about 1.4 ms — which is the point of the
measurement, not a footnote to it: the cost tracks **depth**, which grew from
16 to 19, and not row count, which grew by a factor of twelve. That is
ADR-0001's claim, measured.

---

## What was measured, and what was not

The timed operation is the pair of closure-table queries that decide a
placement's cost:

1. `isSelfOrDescendant` — the cross-line guard, a point lookup on the
   `(ancestor_id, descendant_id)` primary key.
2. The ancestor read in `writeClosureRows` — `WHERE descendant_id = ?`, served
   by `idx_closure_descendant`, returning one row per ancestor.

Everything else in `PlacementEngine::place()` — the `distributors` insert, the
sponsorship row, the audit log, the event dispatch — is constant work that does
not touch the tree and does not grow with it. Including it would have inflated
the number without telling us anything about the structure under test.

**Two things this does not prove**, and they should not be read into it:

- **It is not a concurrency test.** The advisory lock in `place()` serialises
  placements targeting the same `placement_id`. Under a registration burst
  where many joiners share one sponsor, the queue behind that lock — not the
  query — is what sets latency. A load test would be a separate exercise.
- **It is a local Docker MySQL**, not the production RDS instance. Absolute
  numbers will differ. The margin here is wide enough (139× the budget) that
  the conclusion survives a much slower disk, but the shape of the curve is the
  durable finding, not the millisecond figure.

---

## How the tree was built

A perfect binary tree, seeded directly into `distributors` and
`genealogy_closure` rather than by calling `place()` a million times — a
million real placements would have taken hours and would have been measuring
the seeder. The rows written are exactly the rows the engine writes, so the
query planner sees the table it will see in production.

Perfect rather than lopsided on purpose: every slot below the last level is
full, so the ancestor set at each node is at its deepest and the spillover walk
has the furthest to go. A realistically ragged tree would have produced a
flattering number.

## Safety

The command **refuses to run against any database whose name does not end in
`_perf`**, and says so rather than proceeding. It truncates three tables, and
the dev database on this machine is one character away from the benchmark one.
Verified: pointed at `arovolife`, it exits with an error and touches nothing.

The throwaway `arovolife_perf` database was left in place, empty — the command
truncates after measuring unless `--keep` is passed. Re-running the proof is
one command; no setup.

---

## Re-running it

```bash
# One-time, if the database has been dropped:
docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "CREATE DATABASE arovolife_perf CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
      GRANT ALL ON arovolife_perf.* TO \"arovolife\"@\"%\";"'
docker compose exec -e DB_DATABASE=arovolife_perf app php artisan migrate --force

# The proof:
docker compose exec -e DB_DATABASE=arovolife_perf app \
  php artisan genealogy:benchmark --nodes=1000000 --samples=500
```

Exit code 1 if p95 breaches the budget, so it can be wired into CI as a
regression gate rather than a thing somebody remembers to check.
